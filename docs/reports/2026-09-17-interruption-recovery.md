# 原窗口中断与普通回复的续聊恢复

日期：2026-09-17。

## 问题与修复

原 Agent 收到用户打断后可能给出普通正文，没有对应剧情。旧网页将其呈现为 `advance=error`，仅提供「查看原文」，前端关闭输入、后端拒绝发送，形成无法继续的终点。此外，暂存后未正式发布的剧情可能停留在 staged，历史 mismatch 也会持续触发提示。

修复后的行为：

- 原回复完整保留，显示系统精灵的续聊入口；不猜测它属于乔布斯还是小黑，也不冒充通过剧情校验。
- 最新的未匹配回复可以继续填写答案，或点击「恢复角色对话」。发送前明确告知会附带格式恢复提醒，仍只使用原任务的一次回复额度。
- 服务器核对存档、发送租约、最新消息和被回复条目后，将用户回答与一次格式提醒作为同一消息交给原 Agent；没有后台自动重试或独立模型会话。
- 原任务保留实际完整发送内容；网页只有在原消息获得确认并与提交关联后，才在「你说」中展示用户填写的回答。不会靠通用文本截断隐藏用户内容。
- 下一次原用户发言会终止未发布剧情的匹配范围，标为 interrupted。晚到的旧台词不能跨用户回合错误套用。新剧情必须使用新的 turn_id，并继续匹配正式 finalText 才播放。
- 历史 mismatch / interrupted 保留为记录，不再阻止下一轮或反复显示已结束的错误提示。停留在普通回复时，原窗口若出现新消息，网页也能显示「点击继续」。

## 验证

`npm test` 共 54 项通过，TypeScript 检查、构建、前端脚本语法和 Skill 校验通过。本次新增 5 项自动验证覆盖：

1. 普通回复原文保留，只有最新条目及有效租约可显式续聊。
2. 用户打断会终止待发布剧情；晚到的同文回复不能将旧剧情复活。
3. 新的合规回合可继续；早于打断发生的正式回复仍正常提交；旧错误不持续阻塞。
4. 单条恢复消息附带格式指令、确认与显示映射正确、重复提交只发一次，后续角色剧情正常匹配。
5. 发送结果未知时，重连与重复点击不会自动重发，草稿保留。

`scripts/recovery-fixture.ts` 为确定性、无模型的浏览器复现工具。实际验证了两条路径：空输入点击「恢复角色对话」，以及填写回答点击「发送」。两者均显示正确的「你说」文字，随后恢复乔布斯的提问与输入框；原回复阅读可用。720 × 950 窗口中的原文、恢复按钮和输入框可见，浏览器无脚本错误。

## 生效与边界

- 本机 Codex、WorkBuddy 已安装的 Skill 同步更新。当前维护任务的网页后台已经重启；其他原任务没有被擅自发送新消息或迁移绑定。
- 已经运行的旧后台需要在**对应原任务**中 `npm run stop` 后按该宿主原有方式重新启动，使用原数据目录。WorkBuddy 仍使用其后台工具运行 `npm run launch -- serve`。只刷新网页无法升级后台；新版前端和启动器会识别缺少恢复能力并给出提示。
- 没有在用户正在审查的真实原任务中主动发送新的恢复请求。本次浏览器操作使用无模型夹具；实际大模型是否完全遵守格式仍不能保证。若它再次输出普通正文，网页继续保留原文并允许用户再次主动续聊，不会自动耗费额度反复修复。
- 不将普通正文视作已完成设计或已交付文档；原有阶段职责与设计闭合检查保持。
