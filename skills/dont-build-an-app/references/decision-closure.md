# 让审查结束时已经有可执行的产品设计

第二阶段开始读取并在后台维护；第三阶段告别前再次核对。这里约束的是设计是否齐备，不是要求用户先开发原型，也不是新增一轮表单审批。

## 每发现一个空白，先判断由谁解决

| 类型 | 处理时机与方式 | 结束审查时的状态 |
|---|---|---|
| 会改变目标人群、首版范围、核心行为、使用负担、数据边界或费用承诺的产品决定 | 在相关的第二/三阶段用具体问题讨论；已有明确答案直接沿用 | 已确认，或用户明确授权裁量后已作出具体选择 |
| 不改变上述约束的常规、可逆实现选择 | AI 根据现有项目、相关偏好和通行习惯决定，不逐项问用户 | 已选默认实现，或给接手 AI 明确的选择规则、边界与退路 |
| 必须经过运行才能知道的事实，如识别效果、耗电、性能 | 明确设计要达到的结果、验证方法和不达标时的处理 | 已转为可执行验证任务；实测结果如实标为未测 |
| 账号、凭据、设备、付费开通或发布许可等执行依赖 | 先确定用途、可接受范围和缺少时能做的部分 | 写明接入节点、所需输入及已有退路；不伪造授权或资源 |

同一个技术词可能属于不同类型。具体转写 SDK 可由开发 AI 选；录音能否上传、用户要不要持续付费、无法联网时能做什么，是产品决定。操作系统可能已由用户的设备与明确自用范围确定；不能仅凭作者用 Windows 就替所有目标用户选 Android。

“你决定”是范围明确时的有效授权：据此选一个具体方案，说明关键取舍，记录为“用户授权，AI 决定”。不逼用户复述自己的决定；也不能把一句“好”扩大为所有未知的授权。旧偏好只是相关依据，不等于本次同意上传数据、付费或改变用途。

## 把重要问题放回它出现的地方

不要等准备告别才第一次做完整性检查。每得到一个新设计，顺带检查它引入的关键前提；每轮只沟通最重要的 1–3 个关联问题。第二阶段确定服务对象、主要载体、使用情境、首版范围和体验承诺；第三阶段走通它，解决会破坏承诺的实际行为。

下面以会议录音待办为例，说明哪些空白不能藏进最后的“开发时再确认”。这是维护示例，不能把这些答案或功能默认套给别的产品：

| 已提出的设计 | 需要提前闭合的产品决定 | 不必逐项盘问的实现细节 |
|---|---|---|
| 手机录会议，散会后得到自己的待办 | 首版在哪类设备使用；典型会议形式、时长范围与环境；何时拿到什么结果 | 满足范围的工程框架、目录和构建工具 |
| 先填个人信息、录声纹 | 真正必需的信息是什么；拒绝提供时能否使用；身份或归属判断不清时的用户结果 | 常规表单控件、字段内部命名 |
| 录音被打断 | 已有内容是否保留；用户能否发现中断；如何继续；是否会漏掉一段却装作完整 | 具体平台回调、持久化库 |
| 自动提取任务 | 不确定、漏提、误提、没有任务时各怎样处理；用户如何核对和完成自己的工作 | 在已定行为内的模型适配和内部数据结构 |
| 调用模型或转写 | 本地/外部处理边界、允许的费用范围、等待与失败行为 | 满足这些约束的提供商/SDK 选择，可按明确规则委托开发 AI 核对后选择 |
| 保存录音和声纹 | 保存在哪类位置、多久、由谁控制、删除涉及哪些数据；拒绝相关权限时怎么办 | 实际目录、表名与索引 |

普通操作已足够明确就收下。例如“错误待办直接删除”，没有新后果就不再追问按钮颜色、摆放、是否点第二次确认。删除待办是否同时销毁原录音，只有确有歧义或影响已定数据规则时才问。关心细节不是把每个控件变成一道题。

## 不把验证当作推迟决定的理由

- “最多支持怎样的一场会”是设计范围；“在这类会议上实测能录多久”是验证结果，不能混写为一个 TBD。
- “不确定的归属给用户什么结果”是产品行为；识别阈值可通过确定的样本、评估方法与选择规则调整，但不能到开发中才决定把不确定结果静默丢掉还是当作事实。
- 验收数字可以是明确标注的设计目标，不必假装已经达到。没有数字依据时，使用可检查的行为标准或相对基线，以及测量后选择参数的规则；不能只写“后面再定”。
- 关键能力尚无可行依据、连合理实现路线都无法确定时，在告别前说明并处理：补查、缩小首版、选可行退路，或由用户明确选择先验证的阶段性方案。不能在已宣布全关通过后突然把整份交付改成调研建议。

## 告别前的静默检查

只对本创意适用的内容检查：

1. 接手 AI 能确定为谁、在哪、做什么；首版与范围外清楚。
2. 主任务的触发、输入、动作、反馈、输出与结束已经连贯；重要分支不靠接手者猜。
3. 场景中最重要的失败、中断、纠错、权限和数据行为有具体处理。
4. 必需的产品决定没有未决项；每项依据是用户答案、有效委托，或有据可循的常规裁量。
5. 实现裁量有边界；验证任务有方法与结果处理；外部执行依赖不会伪装成未回答的产品问题。
6. 已有足够信息整理功能、页面/交互、状态和可检查验收。无需用户再从头讲一遍。

使用 `decision_register` 保存重要项：`id / 内容 / 类型 / 适用场景 / 选择或规则 / 来源 / 状态 / 影响`；状态可为 `未决 / 已确认 / 已授权决定 / 已定裁量规则 / 已转验证任务 / 执行依赖 / 不适用`。只记录有用的决定，不为普通控件建立繁琐账本。

如果仍缺关键答案，先留在对话里解决：产品目的或范围的缺口由乔布斯追问，具体使用结果由小黑追问。只回到受影响的问题，不重演整段开场。此时还不能说“没啥好问的了”。

正常完成后交付“可执行产品设计方案”。设计就绪、检索证据状态、真实验证状态分别记录：查重待定且用户已选择继续，可以设计就绪，但不能宣称原创；实测未做，也不等于设计没完成。

用户明确暂停就暂停；明确跳过或提前索要成果则交付标明缺口的阶段性草案。两种例外都不能伪装成已完成审查，更不能为了标题好看而代填产品答案。
